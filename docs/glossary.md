# Scrum 项目管理术语表

本文整理 Scrum 项目管理软件中常见英语术语及其中文解释。不同组织的译法可能略有差异，产品界面与项目文档应统一采用同一套译名。

## Scrum 基本术语

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Scrum | 敏捷开发框架 / Scrum 框架 | 一种通过短周期迭代和持续反馈来开发复杂产品的工作框架。 |
| Agile | 敏捷 | 强调快速反馈、持续交付和适应变化的一组价值观及工作方式。Scrum 是敏捷实践的一种。 |
| Scrum Team | Scrum 团队 | 由产品负责人、Scrum Master 和开发者组成的团队。 |
| Sprint | 冲刺 / 迭代 | 一个固定时长的开发周期，通常为 1～4 周。团队在周期内完成一个可用的产品增量。 |
| Sprint Goal | 冲刺目标 / 迭代目标 | 本次 Sprint 希望实现的核心业务成果，而不是简单的任务清单。 |
| Product Goal | 产品目标 | 产品在较长时期内希望达到的目标，为 Product Backlog 提供方向。 |
| Increment | 产品增量 | 一个 Sprint 结束时新增且可用的产品成果。 |
| Empiricism | 经验主义 | 根据实际观察、检查和反馈作出决策，而不是完全依赖预先计划。 |

## Scrum 角色

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Product Owner | 产品负责人 | 对产品目标、需求价值和待办事项优先级负责的人，简称 PO。 |
| Scrum Master | Scrum Master / 敏捷教练 | 帮助团队正确实践 Scrum、消除流程障碍并促进持续改进的人。 |
| Developer | 开发者 / 交付成员 | 负责完成产品增量的团队成员，不仅指程序员，也包括测试、设计等人员。 |
| Stakeholder | 利益相关者 / 干系人 | 关注产品结果但不属于 Scrum Team 的人员，如客户、管理层、销售和运营人员。 |
| Project Manager | 项目经理 | 负责计划、资源或交付协调的业务职位，但不是 Scrum 官方定义的角色。 |
| Project Administrator | 项目管理员 | 负责项目成员、权限、工作流和系统配置的软件管理角色。 |
| Workspace Administrator | 工作空间管理员 | 管理一个工作空间内的用户、项目、模板和安全设置的人员。 |

## 需求和工作项

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Work Item | 工作项 | 对需求、任务、缺陷等可跟踪对象的统称。 |
| Product Backlog | 产品待办列表 | 产品全部待处理需求和工作的有序列表，由 Product Owner 负责管理。 |
| Sprint Backlog | 冲刺待办列表 | 团队为完成当前 Sprint Goal 而选择的工作及其执行计划。 |
| Backlog Item | 待办事项 | Product Backlog 中的单个工作项。 |
| Epic | 史诗 / 大型需求 | 范围较大、通常需要拆成多个功能或用户故事的业务主题。 |
| Feature | 功能 | 能为用户提供相对完整价值的一组能力。 |
| User Story | 用户故事 | 从用户视角描述需求的方式，通常表达“谁需要什么，以及为什么需要”。 |
| Task | 任务 | 为实现一个用户故事而执行的具体工作。 |
| Subtask | 子任务 | 对任务进一步拆分得到的更小工作单元。 |
| Bug | 缺陷 / 故障 | 产品实际行为与预期行为不一致的问题。 |
| Spike | 调研任务 / 技术预研 | 为解决不确定性而进行的研究、实验或技术验证工作。 |
| Acceptance Criteria | 验收标准 | 判断一个需求是否满足业务预期的具体、可验证条件。 |
| Business Value | 业务价值 | 一个需求对客户、产品或企业产生的价值。 |
| Priority | 优先级 | 表示工作项处理顺序或紧急程度。 |
| Dependency | 依赖关系 | 一个工作项必须依赖另一个工作项、系统或外部条件才能完成。 |
| Risk | 风险 | 可能影响范围、时间、质量或目标实现的不确定因素。 |
| Label / Tag | 标签 | 用于分类、搜索和筛选工作项的标记。 |
| Assignee | 负责人 / 经办人 | 当前负责处理工作项的人。 |
| Reporter | 报告人 / 创建人 | 提出或录入工作项的人。 |

## 估算与容量

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Estimation | 估算 | 团队对工作复杂度、规模或投入的相对判断。 |
| Story Point | 故事点 | 综合复杂度、工作量和不确定性的相对估算单位，不等同于小时。 |
| Capacity | 团队容量 | 团队在一个 Sprint 中实际可投入的工作能力。 |
| Velocity | 迭代速率 | 团队过去若干 Sprint 实际完成的故事点数量，用于辅助未来规划。 |
| Planning Poker | 计划扑克 | 团队成员独立出示估算值，再讨论差异并达成共识的估算方法。 |
| Commitment | 承诺 | 团队对目标的责任。在 Scrum 中更强调承诺 Sprint Goal，而非保证完成每个任务。 |

## Scrum 活动

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Sprint Planning | 冲刺计划会 / 迭代计划会 | 确定 Sprint Goal、选择工作并形成 Sprint Backlog 的会议。 |
| Daily Scrum | 每日 Scrum / 每日站会 | Developers 每天检查目标进展并调整工作计划的短会，通常不超过 15 分钟。 |
| Sprint Review | 冲刺评审会 / 迭代评审会 | 展示产品增量、收集利益相关者反馈并调整后续方向的活动。 |
| Sprint Retrospective | 冲刺回顾会 / 迭代回顾会 | 团队检查协作和流程问题，并制定改进行动的会议。 |
| Backlog Refinement | 待办列表梳理 / 需求细化 | 澄清、拆分、估算并调整 Product Backlog 的持续活动。 |
| Retrospective Action | 回顾改进行动 | 回顾会议后形成的具体改进任务。 |
| Action Item | 行动项 | 需要指定负责人并跟踪完成的后续事项。 |

## 完成标准与准备标准

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Definition of Done | 完成定义 | 团队对“真正完成”的统一质量标准，简称 DoD。 |
| Definition of Ready | 就绪定义 / 准备完成标准 | 团队判断工作项是否足够清晰、可以进入 Sprint 的参考条件，简称 DoR。它不是 Scrum 官方必需元素。 |
| Done | 已完成 | 工作已经符合 Definition of Done，而不只是代码编写完成。 |
| Ready | 已就绪 | 工作项已经澄清、可估算，并具备开始实施的条件。 |
| Acceptance | 验收 | 确认产品成果满足约定的业务要求和验收标准。 |
| Reopen | 重新打开 | 已关闭或完成的工作项因问题而恢复到待处理状态。 |

## 工作流状态

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| To Do | 待处理 | 尚未开始的工作。 |
| In Progress | 进行中 | 已经开始处理的工作。 |
| In Review | 评审中 | 正在进行代码、设计或业务评审。 |
| Ready for Test | 待测试 | 开发工作已结束，等待测试。 |
| Testing | 测试中 | 正在执行功能、接口或回归测试。 |
| Blocked | 被阻塞 | 因依赖、权限、环境或决策问题暂时无法继续。 |
| Done | 已完成 | 已满足团队的完成定义。 |
| Closed | 已关闭 | 工作流程已经结束，通常不再继续处理。 |
| Rejected | 已拒绝 | 工作项或成果未被接受。 |
| Canceled | 已取消 | 工作不再需要执行。 |

## 版本与发布

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Roadmap | 产品路线图 | 展示产品目标、重要功能和大致时间方向的规划视图。 |
| Release | 发布 / 版本发布 | 将一组已经完成的功能提供给用户使用。 |
| Target Version | 目标版本 | 计划包含某个工作项的产品版本。 |
| Release Note | 发布说明 | 向用户说明新功能、改进、缺陷修复和已知问题的文档。 |
| Milestone | 里程碑 | 项目中的重要阶段、日期或成果节点。 |
| Deployment | 部署 | 将软件安装或发布到某个运行环境的过程。 |
| Build | 构建 | 将源代码编译、打包成可测试或可部署产物的过程。 |

## 开发协作

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Branch | 代码分支 | 从代码主线分出的独立开发路径。 |
| Commit | 代码提交 | 对一组代码变更及其说明的记录。 |
| Pull Request / Merge Request | 合并请求 | 请求团队评审并将一个分支的代码合入另一个分支，简称 PR 或 MR。 |
| Code Review | 代码评审 | 由其他开发者检查代码质量、逻辑和风险。 |
| Continuous Integration | 持续集成 | 频繁合并代码，并自动执行构建和测试，简称 CI。 |
| Continuous Delivery | 持续交付 | 使软件始终保持可部署状态的实践，简称 CD。 |
| Regression Testing | 回归测试 | 验证新改动没有破坏原有功能。 |
| Rollback | 回滚 | 当发布出现问题时恢复到先前稳定版本。 |

## 报表与指标

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Burndown Chart | 燃尽图 | 展示 Sprint 剩余工作量随时间减少的趋势。 |
| Burnup Chart | 燃起图 | 展示已完成工作量和总范围变化的趋势。 |
| Cumulative Flow Diagram | 累积流图 | 展示不同状态下工作项数量变化，用于发现流程瓶颈，简称 CFD。 |
| Cycle Time | 周期时间 | 工作项从“开始处理”到“完成”所花的时间。 |
| Lead Time | 前置时间 / 交付周期 | 从需求提出到最终交付的总时间。 |
| Throughput | 吞吐量 | 单位时间内完成的工作项数量。 |
| Work in Progress | 在制工作 | 已经开始但尚未完成的工作，简称 WIP。 |
| WIP Limit | 在制品限制 | 限制某个流程阶段同时进行的工作数量，避免任务堆积。 |
| Sprint Health | Sprint 健康度 | 综合目标进展、阻塞、燃尽趋势和容量等信息形成的状态判断。 |

## 权限与安全

| 英语术语 | 常用中文 | 中文解释 |
|---|---|---|
| Permission | 权限 | 用户是否可以执行某项操作。 |
| Role | 角色 | 一组职责和权限的集合。 |
| RBAC | 基于角色的访问控制 | 将权限授予角色，再把角色分配给用户的权限模型。 |
| Resource | 资源 | 权限控制的对象，例如项目、Sprint、工作项和附件。 |
| Scope | 作用范围 | 权限在哪个组织、工作空间、项目或资源中有效。 |
| Least Privilege | 最小权限原则 | 只授予用户完成工作所必需的权限。 |
| Audit Log | 审计日志 | 记录谁在何时进行了什么敏感操作。 |
| Soft Delete | 软删除 | 数据删除后进入回收或隐藏状态，仍可恢复。 |
| Hard Delete | 永久删除 | 从系统中彻底移除数据，通常不可恢复。 |
| User Group | 用户组 | 将多个用户组成一组，统一分配角色和权限。 |
| Workspace | 工作空间 | 用来集中管理多个项目、成员和配置的组织容器。 |
| Guest | 访客 | 仅能访问明确授权内容的外部或受限用户。 |

## 容易混淆的概念

- **Product Backlog 与 Sprint Backlog**：Product Backlog 是产品的全部待办；Sprint Backlog 是当前 Sprint 为实现目标而选择的工作。
- **Acceptance Criteria 与 Definition of Done**：Acceptance Criteria 是单个需求的验收条件；Definition of Done 是所有工作普遍适用的完成质量标准。
- **Story Point 与时间**：Story Point 表示相对复杂度、工作量和不确定性；小时或天表示实际时间，两者不应直接等同。
